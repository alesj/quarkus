= Observability Dev Services with Elastic
include::_attributes.adoc[]
:summary: Instructions on how to use the Elastic observability stack
:topics: observability,elastic,elasticsearch,kibana,apm,otlp,opentelemetry,devservices,micrometer
:extensions: io.quarkus:quarkus-observability-devservices

This Dev Service provides an `all-in-one` Elastic observability Docker image containing https://www.elastic.co/elasticsearch[Elasticsearch], https://www.elastic.co/kibana[Kibana], and https://www.elastic.co/apm[APM Server]. APM Server natively accepts OpenTelemetry data (both gRPC and HTTP on the same port), so it acts as an OTLP-compatible collector forwarding traces, metrics and logs into Elasticsearch, where they can be visualized through Kibana.

== Configuring your project

Add the Quarkus Elastic sink extension to your build file:

[source,xml,role="primary asciidoc-tabs-target-sync-cli asciidoc-tabs-target-sync-maven"]
.pom.xml
----
<dependency>
    <groupId>io.quarkus</groupId>
    <artifactId>quarkus-observability-devservices-elastic</artifactId>
    <scope>provided</scope>
</dependency>
----

[source,gradle,role="secondary asciidoc-tabs-target-sync-gradle"]
.build.gradle
----
implementation("io.quarkus:quarkus-observability-devservices-elastic")
----

=== OpenTelemetry

With OpenTelemetry, metrics, traces and logs can be created and sent to the Elastic stack via APM Server.

By default, the https://quarkus.io/guides/opentelemetry[OpenTelemetry extension] will produce https://quarkus.io/guides/opentelemetry-tracing[traces]. https://quarkus.io/guides/opentelemetry-metrics[Metrics] and https://quarkus.io/guides/opentelemetry-logging[logs] must be enabled separately.

The `quarkus-opentelemetry` extension can be added to your build file like this:
[source,xml,role="primary asciidoc-tabs-target-sync-cli asciidoc-tabs-target-sync-maven"]
.pom.xml
----
<dependency>
    <groupId>io.quarkus</groupId>
    <artifactId>quarkus-opentelemetry</artifactId>
</dependency>
----

[source,gradle,role="secondary asciidoc-tabs-target-sync-gradle"]
.build.gradle
----
implementation("io.quarkus:quarkus-opentelemetry")
----

The `quarkus.otel.exporter.otlp.endpoint` property is automatically set to the APM Server endpoint as seen from the outside of the Docker container.

The `quarkus.otel.exporter.otlp.protocol` is set to `http/protobuf` by default (configurable via `quarkus.observability.elastic.otlp-protocol`).

=== Micrometer to OpenTelemetry bridge

This extension provides Micrometer metrics and OpenTelemetry metrics, traces and logs. All data is managed and sent out by the OpenTelemetry extension to the Elastic stack.

**All signals are enabled by default.**

The extension can be added to your build file like this:

[source,xml,role="primary asciidoc-tabs-target-sync-cli asciidoc-tabs-target-sync-maven"]
.pom.xml
----
<dependency>
    <groupId>io.quarkus</groupId>
    <artifactId>quarkus-micrometer-opentelemetry</artifactId>
</dependency>
----

[source,gradle,role="secondary asciidoc-tabs-target-sync-gradle"]
.build.gradle
----
implementation("io.quarkus:quarkus-micrometer-opentelemetry")
----

=== Micrometer OTLP registry

The https://docs.quarkiverse.io/quarkus-micrometer-registry/dev/micrometer-registry-otlp.html[Quarkiverse Micrometer OTLP registry] will output data using the OpenTelemetry OTLP protocol to the APM Server. This will *push* data out of the service:

[source,xml,role="primary asciidoc-tabs-target-sync-cli asciidoc-tabs-target-sync-maven"]
.pom.xml
----
<dependency>
    <groupId>io.quarkiverse.micrometer.registry</groupId>
    <artifactId>quarkus-micrometer-registry-otlp</artifactId>
</dependency>
----

[source,gradle,role="secondary asciidoc-tabs-target-sync-gradle"]
.build.gradle
----
implementation("io.quarkiverse.micrometer.registry:quarkus-micrometer-registry-otlp")
----

When using the https://micrometer.io/[Micrometer's] Quarkiverse OTLP registry, the `quarkus.micrometer.export.otlp.url` property is automatically set to the APM Server endpoint.

== Kibana

=== Kibana UI access

Once you start your app in dev mode:

include::{includes}/devtools/dev.adoc[]

You will see a log entry like this:

[source, log]
----
[io.qu.ob.de.ObservabilityDevServiceProcessor] (build-35) Dev Service Elastic started, config: {elasticsearch.endpoint=http://localhost:49200, kibana.endpoint=http://localhost:45601, apm-server.url=localhost:48200, quarkus.otel.exporter.otlp.endpoint=http://localhost:48200, quarkus.otel.exporter.otlp.protocol=http/protobuf}
----
Remember that Kibana is accessible on an ephemeral port, so you need to check the logs to see which port is being used. In this example, the Kibana endpoint is `kibana.endpoint=http://localhost:45601`.

Another option is to use the *Dev UI* (http://localhost:8080/q/dev-ui/extensions) as the Kibana URL link will be available and if selected it will open a new browser tab directly to the running Kibana instance.

=== Observability in Kibana

In Kibana, navigate to the *Observability* section to explore your telemetry data:

* **APM** -- view traces, service maps, and transaction details
* **Metrics** -- browse metrics forwarded via OTLP
* **Logs** -- search and filter application logs

== Additional configuration

This extension will configure your `quarkus-opentelemetry` and `quarkus-micrometer-registry-otlp` extensions to send data to the APM Server, which natively accepts OTLP on port 8200 (both gRPC and HTTP).

If you don't want all the hassle with Dev Services (e.g. lookup and re-use of existing running containers, etc) you can simply disable Dev Services and enable just Dev Resource usage:

[source,properties]
----
quarkus.observability.enabled=false
quarkus.observability.dev-resources=true
----

By default Quarkus lets Testcontainers expose random ports for Elasticsearch, Kibana and APM Server, but you can force the usage of user-side fixed ports via setting the ports yourself -- but then be aware of port conflicts.

[source,properties]
----
quarkus.observability.elastic.elasticsearch-port=9200
quarkus.observability.elastic.kibana-port=5601
quarkus.observability.elastic.apm-port=8200
----

[NOTE]
====
Internal container ports stay the same: 9200 for Elasticsearch, 5601 for Kibana, 8200 for APM Server.
====

=== Disabling Elastic Dev Services

Elastic Dev Services are enabled when the `quarkus-observability-devservices-elastic` sink is on the classpath. To disable them entirely, set:

[source,properties]
----
quarkus.observability.elastic.enabled=false
----

Or disable all observability Dev Services:

[source,properties]
----
quarkus.observability.enabled=false
----

=== Automatic detection of explicit OTLP endpoint configuration

Elastic Dev Services will not start if an OTLP exporter endpoint is already explicitly configured. This prevents the Dev Service from overriding a custom collector that has been intentionally set by the user.

The following properties are checked, depending on which extensions are present:

[cols="1,1"]
|===
|Extension |Property checked

|`quarkus-opentelemetry`
|`quarkus.otel.exporter.otlp.endpoint`

|`quarkus-opentelemetry`
|`quarkus.otel.exporter.otlp.traces.endpoint`

|`quarkus-opentelemetry`
|`quarkus.otel.exporter.otlp.metrics.endpoint`

|`quarkus-opentelemetry`
|`quarkus.otel.exporter.otlp.logs.endpoint`

|`quarkus-micrometer-registry-otlp`
|`quarkus.micrometer.export.otlp.url`
|===

If any of those properties is explicitly set, Elastic Dev Services will not start. If you need a custom endpoint in production but still want Elastic to start in dev mode, scope the property to the production profile:

[source,properties]
----
%prod.quarkus.otel.exporter.otlp.traces.endpoint=http://my-collector:4318
----

=== Enabling Elastic Dev Services in tests

By default, observability Dev Services do not start in test mode. To enable the Elastic container during tests, set:

[source,properties]
----
quarkus.observability.enabled-in-tests=true
----

For the least 'auto-magical' usage in tests, you can explicitly list Elastic Dev Resource in the test as a `@QuarkusTestResource` resource:
[source, java]
----
@QuarkusTest
@QuarkusTestResource(value = ElasticResource.class, restrictToAnnotatedClass = true)
@TestProfile(QuarkusTestResourceTestProfile.class)
public class ElasticLifecycleTest extends ElasticTestBase {
}
----

=== Dev Resources mode

As an alternative to full Dev Services, you can enable a simplified Dev Resources mode. In this mode, containers are started lazily at runtime via a MicroProfile `ConfigSource` instead of during the build phase.

[source,properties]
----
quarkus.observability.enabled=false
quarkus.observability.dev-resources=true
----

[NOTE]
====
`quarkus.observability.enabled` must be set to `false` when using Dev Resources mode. The two modes are mutually exclusive.
====

=== OTLP protocol

APM Server accepts both gRPC and HTTP on the same port (8200). By default, the protocol is set to `http/protobuf`. You can change it:

[source,properties]
----
quarkus.observability.elastic.otlp-protocol=grpc
----

=== Shutdown timeout

You can configure the grace period for graceful shutdown:

[source,properties]
----
quarkus.observability.elastic.shutdown-timeout=15
----

=== Exposed backend endpoints

The Dev Service exposes the following endpoints:

[cols="1,1"]
|===
|Config property |Description

|`elasticsearch.endpoint`
|Elasticsearch HTTP API (e.g. `http://localhost:49200`)

|`kibana.endpoint`
|Kibana UI and API (e.g. `http://localhost:45601`)

|`apm-server.url`
|APM Server / OTLP endpoint (e.g. `localhost:48200`)

|`elastic.mcp.api-key`
|Base64-encoded Elasticsearch API key for Kibana MCP authentication
|===

These can be injected via `@ConfigProperty`:

[source, java]
----
@ConfigProperty(name = "elasticsearch.endpoint")
String elasticsearchEndpoint;

@ConfigProperty(name = "kibana.endpoint")
String kibanaEndpoint;

@ConfigProperty(name = "apm-server.url")
String apmServerUrl;

@ConfigProperty(name = "elastic.mcp.api-key")
String elasticMcpApiKey;
----

=== MCP integration for AI tools

The Elastic Dev Service supports the https://www.elastic.co/docs/solutions/observability/agents/elastic-ai-assistant[Kibana Agent Builder MCP], allowing AI coding tools like Claude Code and Cursor to query observability data directly from the running Kibana instance.

The MCP endpoint is at `<kibana.endpoint>/api/agent_builder/mcp` and provides purpose-built observability tools:

* `observability.get_traces` -- query distributed traces
* `observability.get_logs` -- search and filter logs
* `observability.get_trace_metrics` -- latency, throughput, failure rates
* `observability.get_services` -- list monitored services
* `observability.get_hosts` -- list monitored hosts
* `platform.core.search` -- generic Elasticsearch search
* `platform.core.execute_esql` -- run ES|QL queries

An Elasticsearch API key with the required privileges is automatically created when the container starts and exposed as the `elastic.mcp.api-key` config property.

To add the Kibana MCP server to Claude Code, use the `kibana.endpoint` and API key from the Dev Service startup log:

[source,bash]
----
claude mcp add --transport http \
  -H "Authorization: ApiKey <elastic.mcp.api-key>" \
  elastic-kibana <kibana.endpoint>/api/agent_builder/mcp
----

[NOTE]
====
Kibana Agent Builder MCP requires Elastic 9.3+. Traces and logs tools require Elastic 9.4+.
====
